## Внедрение RAG-бота
### Исследование моделей и инфраструктуры

#### Цель

Снизить потери времени и стоимость поиска знаний, уменьшить нагрузку на экспертов, улучшить управляемость документации

#### Важные факты для выбора архитектуры
* Разнородные источники и дубли: GitHub / Confluence / Google Drive / PDF legacy / Zendesk
* Есть расхождение версий между источниками
* Часть данных может быть чувствительной (архитектура, внутренние политики, интеграции с клиентами)
* Решение должно "переваривать" рост в 400 страниц/мес без деградации качества и времени ответа

#### Сравнение LLM-моделей

| Критерий                              | Локальные LLM (Hugging Face, self-hosted)                                                                         | OpenAI (cloud API)                                                            | YandexGPT (cloud API)                                                               |
|---------------------------------------|-------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------|-------------------------------------------------------------------------------------|
| **Качество ответов**                  | Может быть очень не плохим при хорошем retrieval, но требует больше настроек                                      | Хорошее качество ответов из коробки, проще быстрее получить хорошее качество  | Хороший компромисс для локализации, но качество ниже чем OpenAI                     |
| **Скорость работы**                   | Зависит от железа; на CPU - медленно, на GPU - быстро                                                             | Обычно быстро, особенно для компактных моделей                                | Обычно быстро                                                                       |
| **Стоимость владения**                | Высокая при использовании GPU (сервер, DevOps, мониторинг, обновления), но дешевле при больших стабильных объёмах | Стоимость по токенам; низкий входной порог, быстро стартовать                 | Стоимость по токенам; часто выгодно для локального рынка                            |
| **Стоимость использования**           | Нет оплат за токены, но есть инфраструктурные затраты                                                             | Тарификация по токенам, на больших объемах может быть большая стоимость       | арификация по токенам, на больших объемах может быть большая стоимость              |
| **Удобство и простота развёртывания** | Высокая кастомизации; cложнее развёртывание: сервера, обновления моделей, безопасность, observability             | Средняя кастомизация, простое развёртывание: API + ключи + SDK                | Средняя кастомизация, простое развёртывание: API/SDK, интеграция через Yandex Cloud |
| **Лучший сценарий применения**        | Конфиденциальные данные, большой постоянный объём                                                                 | Быстрый старт, высокая точность                                               | Региональный кейс, баланс цена/качество/локализация                                 |

**Решение: выбрана локальная LLM, поскольку не желательна отправка данных в облако**

#### Сравнение моделей эмбеддингов

| Критерий                                        | Sentence-Transformers (локально)                                                                                     | OpenAI Embeddings (cloud)                                                     |
| ----------------------------------------------- |----------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| **Скорость создания индекса**                   | Хорошая на GPU, средняя/низкая на CPU                                                                                | Высокая с точки зрения простоты масштабирования, но возможны сетевые задержки |
| **Качество поиска**                             | Хорошее (если правильно подобрать модель под язык/домен)                                                             | Высокое качество поиска                                                       |
| **Стоимость владения**                          | Высокая при использовании GPU (сервер, DevOps, мониторинг, обновления), но дешевле при больших стабильных объёмах    | Стоимость по токенам; низкий входной порог, быстро стартовать                 |
| **Стоимость использования**                     | Нет оплат за токены, но есть инфраструктурные затраты                                                                | Есть официальная низкая стоимость за 1M токенов для embedding-моделей         |
| **Лучший сценарий**                             | Конфиденциальные данные, большой постоянный объём                                                                    | Быстрый запуск, малый/средний объём                                           |

**Решение: выбран Sentence-Transformers (локально), поскольку не желательна отправка данных в облако**

#### Сравнение конкретных моделей эмбеддингов
| Модель                     | Тип                               | Сильные стороны                                                 | Ограничения                                                             |
| -------------------------- | --------------------------------- |-----------------------------------------------------------------|-------------------------------------------------------------------------|
| **all-MiniLM-L6-v2**       | Локальная (Sentence-Transformers) | Очень быстрая, лёгкая, проста в запуске                         | Более слабое качество retrieval по сравнению с более сильными моделями  |
| **text-embedding-3-small** | Облачная (OpenAI)                 | Современная модель, простой запуск через API, хорошее качество  | Требует отправки текста в облако; есть операционные расходы по токенам  |
| **bge-base-en-v1.5**       | Локальная (BAAI)                  | Сильная retrieval-ориентированная модель для английского поиска | Требует локальной инфраструктуры; англоязычная специализация            |

**Решение: выбрана модель bge-base-en-v1.5, поскольку она отвечает необходимым требованиям:**
* Хорошее качество retrieval
* Не требуется отправка данных в облако
* Хорошо подходит для production

#### Сравнение векторных БД: ChromaDB vs FAISS
| Критерий                                                    | ChromaDB                                                  | FAISS                                                                              |
|-------------------------------------------------------------|-----------------------------------------------------------|------------------------------------------------------------------------------------|
| **Скорость поиска и индексации**                            | Хорошая для малого-среднего масштаба                      | Очень высокая, особенно при правильном выборе индекса                              |
| **Сложность внедрения и поддержки**                         | Средняя (удобно стартовать)                               | Высокая (нужно самим строить слой хранения, метаданные, persistence, API)          |
| **Удобство работы**                                         | Высокое: коллекции, клиент, API, удобный UX для RAG       | Средняя: мощно, но нужно самими конструировать                                     |
| **Стоимость владения**                                      | Низкая: можно поднять быстро                              | Выше по инженерным трудозатратам                                                   |
| **Лучший сценарий**                                         | MVP и ранний production RAG, когда важна скорость запуска | High-performance кастомный retrieval-engine, когда есть сильная инженерная команда |

**Решение: выбрана БД ChromaDB, тк. можно быстро и без больших сложностей внедрить (меньше ручных настроек)**

#### Рекомендуемая конфигурация сервера
* CPU: 24–32 vCPU
* RAM: 128–256 GB
* GPU: минимум: 1 мощная GPU (для компактной LLM + embeddings); предпочтительно: 2× GPU (разделить embeddings/reranking и generation)
* Disk: 2 TB NVMe (индексы, модели, snapshots, логи)

### Реализация RAG-бота с техниками промптинга
Выбрана LLM модель Qwen2.5-7B, с запуском через Ollama

Инструкция по запуску:
1. Запустить LLM через docker-compose - bot\LLM\docker-compose.yaml
2. Запустить RAG: bot\venv\Scripts\python.exe bot\telegram_bot.py
3. Использовать telegram bot: https://t.me/quantum_f_bot

#### Примеры даилогов к заданию 4:
* Несколько успешных диалогов.
* Диалоги, когда бот овтечает: «Я не знаю».

#### Анализ результата:
* Тест успешно пройден, все ответ соотвествуют ождиаемым
* По всем вопросам, информация которых есть в базе, бот дал правильный ответ
* Бот дает ответ "Я не знаю" по информации которой нет в базе или она удалена
* Выявленная проблема: в "золотые вопросы" были заложены удалённые/отсутствующие темы - бот корректно отвечал "Я не знаю", но retrieval при этом всё равно возвращал похожие чанки
* Рекомендации по улучшению: 
  * Улучшение базы знаний (покрытие)
  * Ввести rerank: штрафовать чанки, где допустим не встречается ключевое слово запроса
  * Улучшение алгоритам "Я не знаю" и метрик успеха
